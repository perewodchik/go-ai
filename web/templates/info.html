Input Encoding (`input_features`)

What the network actually sees of the position
Default: Standard (10 planes)

The board is handed to the network as a stack of planes — one board-sized 0/1 grid per feature. Everything is encoded from the current player's point of view, so the network sees "my stones" and "their stones" rather than black and white. That halves the effective state space: one network learns both colours at once.

Standard — 10 planes (`v1_10`) Stones, liberty counts, ko point, turn colour. Every model in this project was trained with this.
Recent moves — 12 planes (`v2_12`) The same 10, plus the opponent's last move and your own previous move.
View the full plane list

Plane 9 exists despite the "my/their" trick because komi is not symmetric — without knowing which colour it is, the network cannot judge a close game. A pass has no location, so its history plane is simply empty.

Why 12 and not AlphaGo Zero's 17?

AlphaGo Zero used 17 planes: the last 8 board positions for each colour, plus colour-to-play. Note what is not in that list — no liberty planes and no ko plane. Its history stack was largely how it perceived ko in the first place.

This project already encodes the ko point explicitly and enforces full positional superko in the rules engine, so that motivation is already satisfied. Copying all 8 steps would be paying for a problem that is already solved.

What history still buys here is locality. Go replies are overwhelmingly local — the answer to a move is usually near it — and "where did they just play" is the strongest hint a policy head can get for free. That signal lives almost entirely in the last one or two moves. Steps 3 through 8 of a full stack add very little that the current position does not already state.

Hence v2_12: the part of history that carries the signal, at 2 extra planes instead of 16.

How it affects learning

What should improve. Mostly the policy head. Knowing where the opponent just played gives it a strong prior on where to look, which matters most in the opening and midgame — exactly the phase this project keeps training samples from (only the first board size² moves are stored). A sharper prior also steers MCTS into good lines sooner, so the same simulation budget searches better.

Cost in compute: negligible. Two extra planes widen only the first convolution. The exact number of added parameters scales with filter width (32 filters: +576 · 64: +1,152 · 96: +1,728 · 128: +2,304 · 160: +2,880 — filters × 2 new planes × 3×3 kernel), and the model-creation screen shows the real figure for whatever size you pick, computed by building both networks and diffing their parameter counts rather than stated here as a fixed number. There is no extra board work: the last two moves are read straight out of the move history the game state already keeps. This is not a throughput decision.

What to watch. History gives the value head more incidental cues about game phase, on top of the turn-colour plane it can already latch onto. That is the exact failure mode the collapse guard exists to catch, so keep an eye on value spread in the diagnostics after switching. If within-colour spread collapses toward zero, the value head has found a shortcut again.

Honest expectation. This is a well-supported idea, not a measured result on this project. It has not been A/B'd here yet. The way to settle it is the same protocol as any other change the promotion gate cannot see: copy a model, train one twin on each encoding for the same number of iterations, then play them head-to-head.

Does it need a migration? (Yes — and there is a safe one)

You cannot simply flip this on a trained model. The plane count decides how many channels the first convolution accepts, so changing it makes the saved weights.pt the wrong shape. The checkpoint loader compares a stored architecture tag and refuses to load a mismatch — deliberately, because the alternative is a cryptic shape error or silently corrupted training. That is why the setting is frozen at model creation, next to the architecture preset.

Nothing breaks for existing models. A config.json written before this setting existed has no such field and falls back to v1_10, which is exactly what it was trained with. No migration is required to keep using what you have.

To move a trained model across, there is a widening migration that costs nothing in strength. Because v2_12 appends its planes and leaves planes 0–9 untouched, every existing weight still addresses the right channel. The two new input weights are initialised to zero, so on the day you migrate:

$$\text{out} \;=\; \sum_{c<10} W_c X_c \;+\; 0 \cdot X_{10} \;+\; 0 \cdot X_{11}$$

— the identical function. Same policy, same value, same Elo. The model then learns to use the new planes from a position of strength instead of from random weights. (This identity is asserted numerically in the test suite, not just argued here.)

Preserved Weights, the gated champion, iteration count, Elo, gate Elo, total games, and every stored game.
Lost The optimizer state (Adam re-warms in a few hundred steps) and the replay buffer — its positions were encoded with 10 planes and a stored sample does not remember which move preceded it, so it cannot be reconstructed. It refills from the next iteration's self-play.

Stop training first; the original weights.pt is copied aside automatically. The migration is one-way — going back would mean discarding whatever the network learned from the new planes.

python scripts/migrate_features.py --list
python scripts/migrate_features.py <model> --to v2_12 --dry-run
python scripts/migrate_features.py <model> --to v2_12
⚠ Immutable after model creation — use the migration script to move a trained model.  ·  Existing models default to `v1_10` and are unaffected.

Board Size

Recommended: 9×9

The $N \times N$ grid the AI learns on. Game state complexity grows exponentially ($10^{38}$ for 9×9 vs $10^{170}$ for 19×19). Smaller boards reach high tactical strength in hours.

View Sizing Tradeoffs
Bigger (13–19) Full strategic framework with Fuseki opening play — self-play games take longer and need larger network capacity.
Smaller (7–9) Rapid iteration loops with sharp tactical fights. 7×7 verifies code instantly; 9×9 is the sweet spot for learning full Go concepts quickly.
Options: 7 · 9 · 13 · 15 · 19  ·  ⚠ Immutable after model creation.

Komi

Recommended: 6.5 (9×9) / 7.5 (19×19)

Compensation points given to White for moving second. The fractional $.5$ prevents ties (jigo) and maintains balanced initial position evaluation ($v(s_0) \approx 0$).

View Komi Tradeoffs
Too high (> 7.5 on 9×9) White is structurally favored; value head learns positive White bias regardless of move quality.
Too low (< 5.5 on 9×9) Black dominates almost every game; value head skews opening move evaluations toward Black.
Typical: 6.5 (9×9), 7.5 (19×19)  ·  Always keep fractional .5.

Ruleset & Scoring

Recommended: Chinese (Area)

Chinese rules (Area Scoring) count alive stones plus enclosed territory ($S = \text{Stones} + \text{Territory}$). Japanese rules (Territory Scoring) count empty territory plus captured stones.

View Scoring Tradeoffs
Chinese Area Scoring Deterministic and mathematically clean without requiring manual dead-stone agreement phases. Ideal for autonomous reinforcement learning.
Japanese Territory Scoring Traditional human scoring style, but requires complex dispute resolution for unremoved dead stones.
Self-play training target always uses Chinese Area Scoring internally.

MCTS Simulations per move

Includes Auto-Scaling & FPU
Recommended: 50–150 · Default: 96

Lookahead search tree expansion cycles ($M$) executed per move. This is the single highest-leverage control parameter for move quality vs search wall-clock time.

View Search Dynamics, FPU & Auto-Scaling
Higher (100–400) Creates sharp, accurate visit distributions $\boldsymbol{\pi}$, accelerating policy learning per iteration.
Lower (< 30) Visits remain near-uniform, producing noisy targets that cause policy loss to stagnate near entropy bounds.
Auto-Scaling (`auto_scale_simulations`): Scales search simulations by board area ($\text{sims} = M \times \frac{N^2}{81}$, clamped between 48 and 800) so large boards maintain sharp visit distributions without manual retuning.
First Play Urgency (`fpu_reduction = 0.35`): Initializes unvisited child node values slightly below parent value ($Q = -Q_{\text{parent}} - 0.35$), preventing MCTS from wasting budget exploring every legal move once before deepening.
Range: 10–1000  ·  Live tunable during training.

Exploration Constant ($c_{\text{puct}}$)

Recommended: 1.5

Weights exploration of unvisited candidate moves (prior $P(s,a)$) against exploitation of high-scoring subtree lines ($Q(s,a)$) in the PUCT formula.

View Exploration Tradeoffs
Higher (2.0–3.0) Wider branch exploration; prevents premature convergence to suboptimal early variations.
Lower (0.5–1.0) Focuses search strictly on the network's top-ranked move; may miss tactical alternatives.
Normal range: 1.0–2.0  ·  Default: 1.5  ·  Live tunable.

Temperature ($\tau$) & Smooth Decay Schedule

Recommended: Init 0.8 → Final 0.1 (30 moves)

Controls move sampling randomness via $\pi_a \propto N(s,a)^{1/\tau}$. High temperature ($\tau \approx 0.8$) explores opening variations; lower temperature ($\tau \approx 0.1$) focuses on the top move in mid/late-game.

View Smooth Decay Formula & Preventing Pass Locks
$$\tau(t) = \tau_{\text{init}} + \min\left(1.0, \frac{t}{T_{\text{thresh}}}\right) \cdot (\tau_{\text{final}} - \tau_{\text{init}})$$

Why Smooth Linear Decay Prevents Pass Locks:
Hard temperature cliff drops (e.g. dropping to 0.001 instantly at move 15) freeze MCTS choices mid-fight. If `PASS` receives even 1–2 visits, both bots rigidly pick pass in back-to-back turns, prematurely ending games with 1-liberty groups uncaptured! Smooth decay down to `0.1` maintains tactical vigilance through the endgame.

Tunables: `temperature_init` (0.8), `temperature_final` (0.1), `temperature_threshold` (30 moves).

Self-Play Games per iteration

Recommended: 5–15

Fresh games generated by the champion network each iteration. All positions are appended to a rolling 50,000-state Replay Buffer with $D_4$ dihedral symmetry augmentation.

View Volume Tradeoffs
More (15–50) Stabilizes value loss targets and prevents overfitting to a single game's outcome; iteration time increases proportionally.
Fewer (1–5) Fast iteration loops, but higher target variance and risk of policy oscillation.
Range: 1–100  ·  Default: 5  ·  Live tunable.

Eval Games vs random bot baseline

Recommended: 4–10

Benchmark games played against an anchor random bot (500 Elo) after each iteration to evaluate baseline win rate $W$ and update absolute Elo rating.

View Evaluation Tradeoffs
More (10–20) Tighter confidence intervals on benchmark win rate; reduces Elo curve noise.
Fewer (2–4) Minimizes iteration overhead. Setting to 0 skips the random eval phase entirely.
Range: 0–50  ·  Default: 4  ·  Live tunable.

Parallel Workers all game-playing phases

Recommended: your core count, minus a couple

Governs the shared CPU process pool used by both game-playing phases: Self-play and the Promotion Gate. The slider's maximum is this machine's logical core count, not a fixed number — the pool clamps itself to the cores and to the game count anyway.

View Concurrency Mechanics & Core Scaling
More A batch finishes only when its slowest game completes; utilizing all cores (Performance + Efficiency) significantly shortens wall-clock time.
Fewer (1–3) Leaves CPU headroom for desktop use and runs cooler on fanless laptops. Safe fallback if process pools encounter memory constraints.
This is a CPU number, even on a GPU machine. Workers run on CPU using the CPU-resident champion model — one MCTS at batch size 1 is faster on a core than through a GPU launch, and N workers cannot share one GPU without N contexts and N copies of the weights. The CUDA/MPS training network is never pickled into a worker; the GPU's job is the gradient steps, in the main process.
The pool is shared and long-lived. It is created once per training run rather than once per phase: on Windows (and macOS) a worker is a fresh interpreter that must import torch, so rebuilding an 18-worker pool twice an iteration costs more than the games it runs.
Range: 1–(cores on this machine)  ·  Default: cores − 2  ·  Memory: ~350 MB per active worker process.

Move Restrictions (`restrict_eye_fill`)

Default: Off (Pure RL)

No Own-Eye Filling: Forbids playing into one of a chain's only two eyes. Two eyes make a group unconditionally immortal; filling one blunders life away.

View Theorem & Heuristics Scope
On (Filter Active) Prunes suicide blunders from MCTS tree search, focusing the simulation budget on productive tactical lines.
Off (Pure AlphaZero) Network learns life-and-death purely from self-play outcomes. Completely comparable with legacy runs.
Applied to self-play and both sides of gate matches  ·  Never applied to random eval bot anchor.

No Pointless Self-Atari (`restrict_self_atari`)

Default: Off (Pure RL)

Forbids moves that capture nothing and leave the group they join on a single liberty, when that group is larger than self_atari_max_stones (default 1). A weak network plays these constantly, and each one burns a search slot to hand over stones.

This one is not a theorem. Unlike No Own-Eye Filling, there is no proof behind it — self-atari is genuinely correct in nakade, seki manipulation, eye-space reduction and ko threats. The exemptions cover most of those, but "most" is the honest word.
View Exemptions & Why the Gate Cannot Validate It

What stays playable:

  • Anything that captures — including every ko capture and most snapbacks. If the move takes stones off the board it is doing something.
  • Throw-ins up to self_atari_max_stones — sacrificing one stone to wreck an eye space is ordinary good play.
  • Every move, when it would block them all — if the filter empties the move list it hands the moves back rather than forcing a pass. A position where every move is self-atari is exactly where the assumption is least reliable.
On (Filter Active) Sharper policy targets and more search budget on real moves — the largest sample-efficiency lever available, because self-atari is frequent in exactly the weak-network regime that matters.
Off (Pure AlphaZero) The network learns liberty counting from outcomes alone. Fully comparable with legacy runs.

The promotion gate is blind to this setting's cost. Candidate and champion both play under the filter, so the gate measures relative strength under the handicap — the gate Elo ladder keeps climbing even if the filter is removing moves the model needed. Expect a discontinuous step in win rate vs random at the iteration you switch it on, since only the network is filtered there. The only valid test is training two models from identical weights, one filtered and one not, then playing them head-to-head with the filter off for both sides.

Applied to self-play and both sides of gate matches  ·  Never applied to random eval bot anchor  ·  Never affects human moves, replays or stored games.

Mercy Rule (`resign_enabled`)

Default: Off

Ends a self-play game once a side's own search has said it is lost for several moves running, instead of paying a full MCTS search per move for an endgame nobody can lose. Self-play only — the gate and the random-bot eval never resign, because there a wrong verdict corrupts a measurement rather than a single training game.

It cannot cost you training data at the default settings. Samples stop being collected at move $N^2$, and Earliest Resign defaults to exactly that, so every sample-producing position is already recorded before a resignation can fire. What it does risk is the outcome label: a resigned game is labelled from a prediction, so a value head that wrongly despairs gets to confirm its own mistake across all $N^2$ retained samples. That is what Playout Check measures.

Watch: wrong-resignation rate Reported after every self-play phase. Keep it under ~5%; if it climbs, raise Resign Confidence or Confirming Moves.
Playout Check = 0 You are flying blind — the rule may be discarding winnable games and nothing will ever tell you.
View safeguards & when it actually starts firing

It is self-gating. An untrained value head produces root evaluations averaging around $|v| \approx 0.12$ and essentially never reaches 0.90, so the rule does nothing at all until the network is genuinely confident. Expect no speedup in early training — that is intended, not a misconfiguration.

Collapse interlock. While the Collapse Guard is tripped the rule is suppressed automatically. A collapsed value head emits $\pm 1$ from the turn-colour plane alone, so it would resign every game on sight — and the resulting two-move games would silence the guard's own pass-rate tripwire, hiding the collapse that caused it.

Both Sides Must Agree. Requires the winner's own search to confirm it is winning, so a single broken value head cannot end games by itself.

Streak semantics. Confirming moves are counted from the start of the game, not from the earliest-resign boundary. A side hopeless for forty moves resigns as soon as the boundary opens.

Earliest Resign below 1.0 starts trading training data for speed  ·  Suppressed automatically while the Collapse Guard is tripped  ·  Live tunable.

The AlphaZero Iteration Lifecycle

Each training iteration executes 6 continuous mathematical stages:

1
State Encoding
Board $s_t$ converted into spatial binary tensor $X \in \mathbb{R}^{10 \times N \times N}$ containing stone locations, liberties, ko, and turn color.
2
Dual Forward Pass
ResNet evaluates $f_\theta(s) = (\boldsymbol{p}, v)$, outputting prior move distribution $\boldsymbol{p}(a|s)$ and scalar win prediction $v(s) \in [-1, 1]$.
3
MCTS Lookahead
Runs $M$ simulations using PUCT selection, First Play Urgency (FPU), Dirichlet root noise, and minimax value backpropagation.
4
Action & Replay
Move $a_t$ sampled from visit distribution $\boldsymbol{\pi}$. Sample $(s_t, \boldsymbol{\pi}_t, z_t, q_t)$ stored in 50k Replay Buffer with $D_4$ dihedral symmetry.
5
Target Blended Loss
Adam optimizes weights on mini-batches with blended target $y = 0.6 z + 0.4 q$ to prevent value-head collapse at the root.
6
Gate & Benchmarks
Candidate tested in Promotion Gate ($E_{\text{gate}}$ games vs champion) and Anchor Eval ($E_{\text{eval}}$ games vs random bot) to update Elo.
1. Spatial Input State Representation
Tensor $X \in \mathbb{R}^{10 \times N \times N}$
At move $t$, board position $s_t$ is encoded into a 10-plane binary feature tensor:
$$X(s) = \left[ X_{\text{player}}, X_{\text{opp}}, X_{\text{lib}_1}^P, X_{\text{lib}_2}^P, X_{\text{lib}_{\ge3}}^P, X_{\text{lib}_1}^O, X_{\text{lib}_2}^O, X_{\text{lib}_{\ge3}}^O, X_{\text{ko}}, X_{\text{turn}} \right]$$
  • Planes 0–1 ($X_{\text{player}}, X_{\text{opp}}$): Binary stone locations for current player and opponent ($1$ if present, $0$ empty).
  • Planes 2–4 ($X_{\text{lib}_k}^P$): Liberty count buckets for current player's stone chains (1, 2, or $\ge 3$ liberties).
  • Planes 5–7 ($X_{\text{lib}_k}^O$): Liberty count buckets for opponent stone chains.
  • Plane 8 ($X_{\text{ko}}$): Illegal Ko move mask (blocks infinite capture-recapture cycles).
  • Plane 9 ($X_{\text{turn}}$): Turn plane ($1$ for Black to move, $0$ for White).
2. Dual-Head Residual Network Architecture
ResNet Body + Policy & Value Heads
Feature tensor $X$ passes through a Conv2D stem, $K$ residual blocks with skip connections, then splits into policy and value heads:
$$\text{Stem: } H_0 = \text{ReLU}\big(\text{BatchNorm}(\text{Conv}_{3\times3}(X))\big)$$ $$\text{ResBlock } l: \mathbf{y}_l = \text{ReLU}\big(\text{BN}(\text{Conv}_{3\times3}(H_{l-1}))\big), \quad H_l = \text{ReLU}\big(H_{l-1} + \text{BN}(\text{Conv}_{3\times3}(\mathbf{y}_l))\big)$$
$$\text{Policy Head: } \mathbf{p}(a|s) = \text{Softmax}\Big( W_p \cdot \text{flatten}\big(\text{ReLU}(\text{BN}(\text{Conv}_{1\times1}(H_K)))\big) + \mathbf{b}_p \Big) \in \mathbb{R}^{N^2+1}$$ $$\text{Value Head: } v(s) = \tanh\Big( W_{v2} \cdot \text{ReLU}\big( W_{v1} \cdot \text{flatten}(\text{ReLU}(\text{BN}(\text{Conv}_{1\times1}(H_K)))) + \mathbf{b}_{v1} \big) + b_{v2} \Big) \in [-1, +1]$$
The Policy Head outputs prior probabilities for all $N^2$ board positions plus the Pass move. The Value Head outputs scalar prediction $v(s) \in [-1, +1]$ from the moving player's perspective.
3. MCTS Search, PUCT Selection & FPU
Predictor Upper Confidence Bound
During tree traversal, child moves are selected to maximize the PUCT formula:
$$\text{PUCT}(s, a) = Q(s, a) + c_{\text{puct}} \cdot P(s, a) \cdot \frac{\sqrt{\sum_{b} N(s, b)}}{1 + N(s, a)}$$
  • $Q(s, a) = \frac{W(s, a)}{N(s, a)}$ is the mean accumulated action value from subtree simulations.
  • $P(s, a)$ is the prior probability supplied by the policy head.
  • $N(s, a)$ is the visit count for candidate action $a$.
  • First Play Urgency (FPU reduction = 0.35): Unvisited nodes ($N=0$) estimate $Q(s,a) = -Q_{\text{parent}} - 0.35$, encouraging focus on promising branches instead of exploring every legal move once.
$$\text{Dirichlet Root Noise: } P'(s_{\text{root}}, a) = (1 - \epsilon) P(s_{\text{root}}, a) + \epsilon \cdot \eta_a, \quad \boldsymbol{\eta} \sim \text{Dirichlet}(\alpha=0.3)$$
Injected at the root during self-play ($\epsilon = 0.25$) to ensure opening diversity and prevent deterministic overfitting.
4. Alternating Minimax Decision Tree Lookahead
Alternating 2-Player Tree
How does MCTS anticipate opponent responses?
MCTS constructs an alternating decision tree:
$$\text{Root } s_0 \,(\text{Black}) \xrightarrow{a_1} s_1 \,(\text{White}) \xrightarrow{a_2} s_2 \,(\text{Black}) \xrightarrow{a_3} \dots \xrightarrow{a_L} s_L$$
  1. Selection: From $s_0$ (Black), MCTS picks Black's move $a_1$ via PUCT. At $s_1$ (White), it simulates White's best response $a_2$ via PUCT from White's perspective.
  2. Expansion: Reaching unvisited leaf $s_L$, the neural network evaluates $f_\theta(s_L) = (\boldsymbol{p}, v)$.
  3. Backpropagation: Value $v(s_L)$ negates at alternating plies ($v_{\text{parent}} = -v_{\text{child}}$) because Go is zero-sum.
  4. Action: After $M$ simulations, the move with the highest visit count $N(s_0, a)$ is played.
5. Neural Network Loss with Target Blending
Adam + Blended Value Target
Network parameters $\boldsymbol{\theta}$ are optimized on sampled mini-batches by minimizing the combined loss:
$$\mathcal{L}(\boldsymbol{\theta}) = \underbrace{(y - v_\theta(s))^2}_{\text{Value MSE Loss } \mathcal{L}_v} \;+\; \underbrace{\left( -\sum_{a=1}^{N^2+1} \pi_a \log p_\theta(a|s) \right)}_{\text{Policy Cross-Entropy Loss } \mathcal{L}_p} \;+\; c \|\boldsymbol{\theta}\|^2$$ $$\text{Blended Value Target: } y = \lambda \cdot z + (1 - \lambda) \cdot q$$
  • $z \in \{-1, 0, +1\}$ is the final game outcome (Chinese Area scoring).
  • $q \in [-1, +1]$ is the MCTS root evaluation at that exact board position.
  • $\lambda = 0.6$ (Outcome Weight): KataGo-style blending prevents value-head collapse at the root. Even if one color wins every game, $q$ varies from position to position, forcing the network to evaluate the board rather than relying on turn color.
  • $c \|\boldsymbol{\theta}\|^2$ is $L_2$ weight decay ($c = 10^{-4}$); gradients are clipped at $\|\mathbf{g}\|_2 \le 1.0$.
6. Chinese Area Scoring & Territory Flood-Fill
Area Scoring: $S = \text{Stones} + \text{Territory}$
Scoring evaluates position equity deterministically without requiring manual dead-stone agreement:
$$\text{Black Score} = S_B + T_B, \qquad \text{White Score} = S_W + T_W + \text{Komi}$$ $$\text{Lead} = \text{Black Score} - \text{White Score}$$
4-Step Territory BFS Flood-Fill:
  1. Stone Counting: Count living Black ($S_B$) and White ($S_W$) stones on the grid.
  2. Empty Region Discovery: Run Breadth-First Search (BFS) on all empty intersections to discover connected empty regions $R_1, \dots, R_k$.
  3. Perimeter Inspection: For each region $R_k$:
    • Exclusively Black border stones $\to$ Black Territory ($T_B += |R_k|$).
    • Exclusively White border stones $\to$ White Territory ($T_W += |R_k|$).
    • Touches both Black and White border stones $\to$ Neutral Dame ($T = 0$).
  4. Komi Addition: Add Komi (6.5 on 9×9) to White's total.

Champion vs Candidate (The Promotion Gate)

Gate: 55% Win Share over 20 Games

Training maintains two distinct networks. Only the verified Champion is permitted to generate self-play games. This prevents bad gradient updates from poisoning future training data.

Network RoleAttribute in CodeResponsibilities
Champion trainer.eval_network The reigning best network. Generates all self-play games, defends in gate matches, and plays against humans on the Play page.
Candidate trainer.network The network actively updated by gradient descent each iteration. Never generates self-play until it defeats the Champion.

Gating Match & Elo Step Formula:
Candidate plays gate_games (default 20) against the Champion with alternating colors. If Candidate win share $p \ge 0.55$, it is promoted to Champion. The Champion Elo increases in a step function:

$$\Delta \text{Elo} = 400 \cdot \log_{10}\!\left(\frac{p}{1 - p}\right) \quad (\text{e.g. } 55\% \to +35 \text{ Elo}, \ 70\% \to +147 \text{ Elo})$$
Stored in models/<id>/weights.pt under champion_state_dict and model_state_dict.

Value-Head Collapse: Root Cause & 3-Layer Defense

3 Safeguard Layers

What is Value Collapse? When one color wins nearly all games in a batch, the value head can minimize its MSE loss by ignoring board features and predicting purely from the turn-color plane (outputting $+1$ on Black turns, $-1$ on White). MCTS move values become identical, causing search to degenerate into raw policy.

Layer 1: Target Blending (Root Fix)
value_target_outcome_weight: 0.6 mixes final outcome $z$ with continuous MCTS evaluation $q$. Because $q$ varies position-to-position, the color shortcut cannot minimize loss.
Layer 2: Promotion Gate (Filter)
Because gate matches alternate colors equally, a color-collapsed network wins ~50% and is rejected. It never becomes Champion.
Layer 3: Collapse Guard (Tripwires)
Evaluates probe positions each iteration. Warns if value_std < 0.05 (flat predictions per color) or pass_rate > 25% (excessive passing).
Layer 4: Stall Breaker (Auto-Reset)
After 5 consecutive gate rejections (gate_stall_warning), candidate weights reset back to Champion weights to resume from a known-good state.

Move Restrictions: The Own-Two-Eye Theorem

`restrict_eye_fill`

When enabled, the bot is prohibited from playing into an eye of its own chain if that chain has exactly two eyes.

Why this is a provable theorem rather than a heuristic:
  • Strict Eye Definition: A point $p$ is an eye of chain $C$ iff every on-board neighbor of $p$ belongs to chain $C$.
  • Unconditional Immortality: A chain with 2 strict eyes cannot be captured by the opponent, because playing into either eye is immediate suicide (0 liberties, captures nothing).
  • False Eye Safety: False eyes (surrounded by multiple separate chains) do not meet the strict definition, so connecting moves at false eyes are never forbidden.
Enforced inside MCTS tree expansion, so the suicide move receives zero prior, zero visits, and never appears in policy targets.

🚨 Troubleshooting Matrix (Symptom & Action Guide)

💥 Loss Explosion / NaN / Infs
Critical Red Flag
Observed Symptoms
Policy Loss or Value Loss suddenly displays NaN, Infinity, or spikes to > 50.0.
Root Cause
Learning rate is set too high, causing Adam gradient steps to overshoot local minima and corrupt weights.
Action Required:
Lower Learning Rate in Live Tuning (e.g. from 0.002 to 0.0005). If weights are corrupted with NaN, revert to a previous checkpoint.
📉 Policy Loss Flatlines High (> 3.2 after 15+ Iterations)
Attention Needed
Observed Symptoms
Policy loss stays near the uniform entropy baseline ($\approx \ln(82) \approx 4.4$ on 9×9) and fails to decrease.
Root Cause
MCTS Simulations count is too low (< 30). With few simulations, tree visits remain flat and noisy.
Action Required:
Increase MCTS Simulations to 100–200. This sharpens visit distribution $\boldsymbol{\pi}$ so the policy head has clear targets.
🎲 Win Rate vs Random Bot Stuck at ~50%
Stagnation Warning
Observed Symptoms
After 10+ iterations, the model still loses games to the random bot and win rate hovers between 45%–60%.
Root Cause
Lookahead budget is insufficient to resolve basic captures, or network capacity is undersized for the board size.
Action Required:
Raise MCTS Simulations to at least 100. If on 13×13 or 19×19, ensure you are using at least a Medium network.
🌊 Value Loss Lingers High (> 0.50)
Data Variance
Observed Symptoms
Value loss oscillates wildly between 0.40 and 0.80 instead of smoothly settling into the 0.15–0.30 range.
Root Cause
Replay buffer is underfilled or self-play volume is too low (e.g. 1–2 games), causing overfitting to single game outcomes.
Action Required:
Increase Self-Play Games per Iteration from 5 to 10–15 to populate the buffer with diverse positions.
☯ Extreme Color Bias (100% Black or White Wins)
Komi Mismatch
Observed Symptoms
Self-play balance shows 100% Black wins or 100% White wins across multiple consecutive iterations.
Root Cause
Komi is misconfigured (e.g. set to 0.0 or 15.0), introducing structural unfairness.
Action Required:
Verify Komi is set to 6.5 for 9×9 boards or 7.5 for 19×19 boards.
⚔ Premature Passing / 1-Liberty Hesitation
Temperature Cliff
Observed Symptoms
Bots pass at move 40–50 while 1-liberty enemy groups remain uncaptured, or hesitate on obvious tactical captures.
Root Cause
Temperature dropped to 0.001 prematurely via a hard step, freezing MCTS move selection before fights resolved.
Action Required:
Set Temp Decay Moves to at least 30, and keep Temp Final at 0.1 instead of 0.001.
✅ Healthy Training Benchmark Checklist
All Systems Optimal
Your model is learning properly when all of the following hold:
  • Win rate vs Random Bot: Exceeds 90% by iteration 8–10 and reaches 100% by iteration 15.
  • Policy Loss: Shows a steady downward trajectory from ~3.8 down to 1.2–1.8.
  • Value Loss: Settles into the 0.15–0.30 band without wild spikes.
  • Elo Progression: Climbs smoothly from 500 up past 1000 within 15–20 iterations.
  • Self-play Balance: Black and White win proportions fluctuate near 45%–55% equity.
